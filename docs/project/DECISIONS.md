| D020 | 2026-10-24 | Accepted (implementation) | Opaque sessions: `secrets.token_urlsafe(32)` tokens stored only as SHA-256 hashes; guest sessions last 7 days and instructor sessions 8 hours (fixed, judged by the database clock). | D021 | 2026-10-24 | Accepted (implementation) | CSRF token = unpadded base64url(HMAC-SHA256(key = raw session token, msg = `cloudcart-csrf-v1`)), returned in JSON by `GET /api/v1/session` and `POST /api/v1/admin/login`, required as `X-CSRF-Token` on every state-changing route except login. Same-origin guard: 403 when `Origin` is present and its host[:port] differs from `Host`, or when `Sec-Fetch-Site: cross-site`. Check order: Origin (403), session (401), CSRF (403) | Session-bound without a server secret or stored plaintext token; scheme is not compared because TLS terminates at the gateway. Requires every proxy in front of the API to preserve the `Host` header |
| D022 | 2026-10-24 | Accepted (implementation) | `python -m cloudcart.seed` reads the instructor password from `CLOUDCART_SEED_ADMIN_PASSWORD` (12–256 characters, never echoed; not an API setting). It inserts products only when their SKU is missing (existing stock/price untouched) and upserts instructor `instructor` with a fresh hash. Product images are `/products/<sku>.svg` | Idempotent seed Job; a rotated Secret takes effect on rerun. Existing instructor sessions are not revoked by a rerun (they expire within 8 hours) so redeploys do not log the instructor out |
| D023 | 2026-10-24 | Accepted (implementation) | Cart rules: `PUT /api/v1/cart/items/{product_id}` sets a quantity of 1–10; at most 20 lines; quantity above current stock → 409; `DELETE` returns the updated cart. Every successful change raises the cart `version` by one under a row lock; an untouched cart reports version 0. Request bodies over 16 KiB → 413; request schemas are strict and closed | Gives Task 3 checkout a reliable optimistic version and bounded inputs; checkout re-validates stock and prices server-side |
| D024 | 2026-10-24 | Accepted (implementation) | Checkout contract: `POST /api/v1/orders`, strict closed body `{cart_version: 0…2³¹−1, payment_outcome: "approved"\|"declined"}` and a required `Idempotency-Key` header of 8–128 characters from `[A-Za-z0-9_-]`. Responses: 201 with `Location` and the `OrderView` for a new order; 200 with the same order for a replay; 409 for a stale cart version, an empty cart, insufficient stock, or a key reused with a different body; 402 for a declined simulated payment. Checks run origin (403), session (401), CSRF (403), then header and schema validation (422); malformed JSON is rejected (422) before those checks because FastAPI parses the body first. Keys are unique per guest; a SHA-256 fingerprint of the canonical body decides replay vs conflict. Only accepted orders record their key, so a declined or refused attempt can be retried with the same key | Status code tells the client whether the order is new; 409/402 bodies change nothing, so the storefront can reload the cart and retry. Not recording failures keeps the key table to real orders |
| D025 | 2026-10-24 | Accepted (implementation) | Checkout runs in one transaction with a fixed lock order: guest cart row `FOR UPDATE` (created empty if missing), idempotency lookup, version check, then the cart's product rows `FOR NO KEY UPDATE` in product-id order, guarded `UPDATE products SET stock = stock - n WHERE stock >= n`, order and lines at current server-side prices and names, one outbox event, and an emptied cart (version + 1). Any later stock-changing code (Task 4 stock return) must lock carts before products and products in id order | The cart lock serializes one guest's checkouts, so a concurrent retry finds the committed order; id-ordered product locks prevent deadlocks between multi-product checkouts; `NO KEY UPDATE` does not conflict with the `KEY SHARE` locks cart lines take; the guard and `stock >= 0` CHECK are backstops |
| D026 | 2026-10-24 | Accepted (implementation) | Order storage: `orders` (status `accepted`/`processing`/`fulfilled`/`failed`, `BIGINT` total, unique guest + key), `order_items` (name and unit price at checkout), `outbox_events` (unique `order_id`, `published_at` null until the broker confirms), `receipts` (unique `order_id`, issued by the worker). No `ON DELETE CASCADE` on order tables or from orders to guests. `OrderView` adds `items` to the planned fields; guests read only their own orders (50 newest first), and another guest's order or receipt id returns the same 404 as an unknown id | Orders are durable business records; a future guest cleanup must skip guests with orders. Items let the order page show what was bought before a receipt exists |
| D027 | 2026-10-24 | Accepted (implementation) | Outbox publication: each API process runs one `OutboxPublisher` thread from the FastAPI lifespan. It claims up to 20 unpublished events oldest first with `FOR UPDATE SKIP LOCKED` plus a 60 s lease (`outbox_events.claimed_until`, partial index on unpublished events), builds Celery protocol-2 messages (`cloudcart.orders.fulfill(order_id, enqueued_at)`, task id = event id), and publishes them with Kombu as persistent, `mandatory` messages on a confirm-mode connection. An event is marked published only after RabbitMQ confirms; a failure discards the connection and releases the remaining claims. Every connect, read, write, and confirm is bounded by `CLOUDCART_BROKER_TIMEOUT_SECONDS` (default 5, 1–60); failures back off from `CLOUDCART_PUBLISHER_INTERVAL_MS` (default 1000, 100–60000) doubling to 30 s. `publish_order` is a method of `OrderPublisher`, which owns the connection, and `publish_batch(session_factory, publisher, limit=20)` takes it | No transaction stays open during broker I/O, so a hung broker never blocks checkout. Skip-locked claims keep replicas from double-sending in the normal case; the lease covers a crash after confirmation, at the cost of a duplicate delivery the worker tolerates. The method form avoids process-global broker state (D015) |
| D028 | 2026-10-24 | Accepted (implementation) | Task transport and worker: one durable classic queue `orders` behind a durable direct exchange `orders`; JSON only; no result backend; late acknowledgement, prefetch 1, requeue on worker loss; a task that raises is acknowledged and dropped (only a malformed message or a bug can raise). The solo pool cannot cancel a task when the broker connection drops: the task finishes, its acknowledgement fails, and RabbitMQ redelivers it. Celery schedules every acknowledgement on its event loop, which the solo pool runs only after a task returns, so a worker killed during a task always gets it redelivered. Worker command `python -m cloudcart.jobs.worker`: one Celery solo-pool process, without gossip, mingle, heartbeat events, or remote control; a bootstep wakes the idle event loop every second so SIGTERM (warm shutdown: finish and acknowledge the current task) takes effect within about a second | RabbitMQ 4.3 refuses the transient non-exclusive reply queue that Celery remote control declares, and Task 6 probes must not depend on `celery inspect`. Without the wake-up an idle worker took 7–10 s to notice SIGTERM (Celery's event loop sleeps up to 10 s between timers). A dedicated module replaces `celery -A` because the app is built from validated settings, not at import time |
| D029 | 2026-10-24 | Accepted (implementation) | Fulfillment and retries: each delivery locks the order row. An unfinished order gets an attempt counted in `orders.fulfillment_attempts` and status `processing` (committed), a simulated dispatch of `CLOUDCART_FULFILLMENT_DELAY_MS` (default 1000, 0–5000), then a receipt (`ON CONFLICT DO NOTHING`) and `fulfilled` in one transaction. A failed attempt waits `CLOUDCART_FULFILLMENT_RETRY_BACKOFF_MS` × 2ⁿ⁻¹ (default 1000, 10–10000; so 1, 2, 4 s) inside the worker and rejects the message with requeue. At most four attempts (the first plus three retries): when the fourth fails, or a delivery finds four used, `fail_order` returns the reserved stock (products in id order, D025) and records `orders.failure_reason` (CHECK: present exactly when failed) once. Stock writers lock the order row before products. Database errors outside a recorded attempt (PostgreSQL unreachable, or refusing the statements, for example a worker started before its migration) do not count: the worker waits the longest backoff (4 × base) and requeues until PostgreSQL accepts it. An attempt that has been recorded counts whatever ends it, including a database outage during it. A task for an unknown order is logged and acknowledged. Finished orders never change again. Rare edge: a duplicate delivery that finds four attempts used while the fourth is still running fails the order (still exactly one final transition) | The message is acknowledged only after a final outcome is committed, so no retry can be lost between republish and acknowledgement (as with Celery's `self.retry`), and the durable counter bounds crash loops that redelivery alone would repeat forever. Without its database the worker can neither process nor record a failure, so a PostgreSQL Pod replacement (Task 8) delays queued orders instead of failing them; only an attempt already under way when PostgreSQL drops is used up. Cost: a solo worker is busy during backoff, and a permanently broken database URL keeps requeueing (visible in logs and RabbitMQ redeliveries) |
| D030 | 2026-10-24 | Accepted (implementation) | Broker configuration: `CLOUDCART_BROKER_URL` (an `amqp://` or `amqps://` URL with a host, a secret) is optional in settings because migrations and the seed do not use it. `CLOUDCART_PUBLISHER_ENABLED` (default true) makes the API require it at startup; the worker always requires it. Both refuse to start with a `ConfigurationError` naming the variable, never its value | An API that accepts orders but can never publish them fails loudly instead of leaving every order "awaiting publication" |
| D031 | 2026-10-24 | Accepted (implementation) | Fault injection for Task 4 tests stays in the test tree: a loopback TCP proxy (`tests/faults.py`) cuts or stalls connections to the disposable RabbitMQ or PostgreSQL, and `tests/worker_harness.py` starts the real worker with test-only dispatch failures or a SIGKILL right after a task's commit (Celery `task_postrun`, before the acknowledgement). The application has no failure knob | Outages and crashes are deterministic and never touch the shared containers or other tests. If the Task 11 dashboards need failed orders on demand, a bounded lab setting can be added then |
