| D019 | 2026-10-24 | Accepted (implementation) | Instructor passwords hashed with `argon2-cffi` 25.1.0 (argon2id, library default parameters); an unknown username still verifies against a fixed dummy hash and every login failure returns the same 401 | Maintained library (passlib is unmaintained) with ARM64 wheels. Defaults use 64 MiB per hash: bound concurrent logins and set explicit parameters before Task 8 sizes API memory limits. Parameters can change freely because the seed rehashes on every run |
| D020 | 2026-10-24 | Accepted (implementation) | Opaque sessions: `secrets.token_urlsafe(32)` tokens stored only as SHA-256 hashes; guest sessions last 7 days and instructor sessions 8 hours (fixed, judged by the database clock). Cookies `cloudcart_guest` and `cloudcart_instructor` are HttpOnly, `SameSite=Strict`, `Path=/`, and `Secure` unless `CLOUDCART_COOKIE_SECURE=false`. Only `GET /api/v1/session` creates a guest; an expired session is never revived (new guest id, empty cart) | High-entropy tokens need no slow hash. Secure by default matches the HTTPS gateway; Strict works because the storefront's API calls are same-site |
| D021 | 2026-10-24 | Accepted (implementation) | CSRF token = unpadded base64url(HMAC-SHA256(key = raw session token, msg = `cloudcart-csrf-v1`)), returned in JSON by `GET /api/v1/session` and `POST /api/v1/admin/login`, required as `X-CSRF-Token` on every state-changing route except login. Same-origin guard: 403 when `Origin` is present and its host[:port] differs from `Host`, or when `Sec-Fetch-Site: cross-site`. Check order: Origin (403), session (401), CSRF (403) | Session-bound without a server secret or stored plaintext token; scheme is not compared because TLS terminates at the gateway. Requires every proxy in front of the API to preserve the `Host` header |
| D022 | 2026-10-24 | Accepted (implementation) | `python -m cloudcart.seed` reads the instructor password from `CLOUDCART_SEED_ADMIN_PASSWORD` (12–256 characters, never echoed; not an API setting). It inserts products only when their SKU is missing (existing stock/price untouched) and upserts instructor `instructor` with a fresh hash. Product images are `/products/<sku>.svg` | Idempotent seed Job; a rotated Secret takes effect on rerun. Existing instructor sessions are not revoked by a rerun (they expire within 8 hours) so redeploys do not log the instructor out |
| D023 | 2026-10-24 | Accepted (implementation) | Cart rules: `PUT /api/v1/cart/items/{product_id}` sets a quantity of 1–10; at most 20 lines; quantity above current stock → 409; `DELETE` returns the updated cart. Every successful change raises the cart `version` by one under a row lock; an untouched cart reports version 0. Request bodies over 16 KiB → 413; request schemas are strict and closed | Gives Task 3 checkout a reliable optimistic version and bounded inputs; checkout re-validates stock and prices server-side |
| D024 | 2026-10-24 | Accepted (implementation) | Checkout contract: `POST /api/v1/orders`, strict closed body `{cart_version: 0…2³¹−1, payment_outcome: "approved"\|"declined"}` and a required `Idempotency-Key` header of 8–128 characters from `[A-Za-z0-9_-]`. Responses: 201 with `Location` and the `OrderView` for a new order; 200 with the same order for a replay; 409 for a stale cart version, an empty cart, insufficient stock, or a key reused with a different body; 402 for a declined simulated payment. Checks run origin (403), session (401), CSRF (403), then header and schema validation (422); malformed JSON is rejected (422) before those checks because FastAPI parses the body first. Keys are unique per guest; a SHA-256 fingerprint of the canonical body decides replay vs conflict. Only accepted orders record their key, so a declined or refused attempt can be retried with the same key | Status code tells the client whether the order is new; 409/402 bodies change nothing, so the storefront can reload the cart and retry. Not recording failures keeps the key table to real orders |
| D025 | 2026-10-24 | Accepted (implementation) | Checkout runs in one transaction with a fixed lock order: guest cart row `FOR UPDATE` (created empty if missing), idempotency lookup, version check, then the cart's product rows `FOR NO KEY UPDATE` in product-id order, guarded `UPDATE products SET stock = stock - n WHERE stock >= n`, order and lines at current server-side prices and names, one outbox event, and an emptied cart (version + 1). Any later stock-changing code (Task 4 stock return) must lock carts before products and products in id order | The cart lock serializes one guest's checkouts, so a concurrent retry finds the committed order; id-ordered product locks prevent deadlocks between multi-product checkouts; `NO KEY UPDATE` does not conflict with the `KEY SHARE` locks cart lines take; the guard and `stock >= 0` CHECK are backstops |
| D026 | 2026-10-24 | Accepted (implementation) | Order storage: `orders` (status `accepted`/`processing`/`fulfilled`/`failed`, `BIGINT` total, unique guest + key), `order_items` (name and unit price at checkout), `outbox_events` (unique `order_id`, `published_at` null until the broker confirms), `receipts` (unique `order_id`, issued by the worker). No `ON DELETE CASCADE` on order tables or from orders to guests. `OrderView` adds `items` to the planned fields; guests read only their own orders (50 newest first), and another guest's order or receipt id returns the same 404 as an unknown id | Orders are durable business records; a future guest cleanup must skip guests with orders. Items let the order page show what was bought before a receipt exists |
